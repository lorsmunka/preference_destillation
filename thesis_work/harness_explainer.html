The tutor harness

The agent is a model plus a harness. The model writes one block per request. The harness does everything else.

TL;DR
  • The model has one job: given a conversation, write one block. The block's opening tag is the decision: <solution> (a new task, or a what-if: a new calculation), <explanation> (a question about the working) or <out_of_scope> (not about this maths).
  • The harness has the rest: it keeps the conversation, decides what the model sees, reads the first tag, asks for the block, checks it, asks once more if the check fails, and stores the result. Off-topic messages it answers itself, with a fixed sentence.
  • Two kinds of history. The main line holds tasks and solutions. The side thread holds questions and explanations. A new task closes the side thread, so the model solves from a clean history. The harness still keeps the full transcript.
  • It does not work token by token. The harness acts between requests. Inside a request the model runs freely until a stop string (</solution>, </explanation>) or its token limit.
  • Training data comes from the same rules. Every training example is a context the harness would build (same Conversation class), so what the student learns on is what it gets at run time.

Who does what

The model

  • reads a tagged conversation that ends in <message>
  • writes one block: a facts-first <solution> or a short <explanation>
  • the opening tag is the route, decided at the second token (every tag starts with <); nothing before or after the block
  • never sees the instructions: the teacher prompt is for Gemma only, and the student learns the behaviour from the examples

The harness

  • the conversation state: main line, side thread, full transcript
  • the context rules: what each request contains
  • the route: reads the first tag, and treats an unclear route as a task (the safe side)
  • off-topic: replies itself, "This question is outside the scope of this task.", and keeps the message out of the model's context
  • the checks: every solution line is well formed and true, and an explanation must not take a checked solution back, nor agree with a pupil's wrong answer
  • asking again: once, at temperature 0.7, if a check fails
  • tidying: fills in a missing "= result" before a solution enters the history

The blocks

<task><solution> <question><explanation> <message> (the newest pupil input, not typed yet) <out_of_scope> (a reply tag only: the harness answers)

Past turns carry their type. The newest input is an untyped <message>, because deciding its type is the model's first decision. Once the harness knows the type, the message enters the history as a <task> or a <question>.

What Gemma reads around the conversation (the teacher prompt, teacher only) 
You are a maths tutor for primary-school pupils. Below is the tutoring conversation so far. The last block, <message>, is the pupil's new message.
- If it is a new task, or asks what the answer would be if a number were different (a new calculation), answer with a <solution> block: first one line for each number you use, written as what it is = number (words from the problem; a number from an earlier answer counts too; numbers without units); then one line per calculation that is needed, written as what it is = calculation = result, using only + - * / (every calculation line ends with = and its result); then the line Answer: <number>; then </solution>. No numbering or bullet points. A division that does not come out even is written like: 23 / 5 = 4 remainder 3. Example:
<solution>
tetras bought later = 4
price of a tetra = 2
money left before = 13
cost of 4 more tetras = 4 * 2 = 8
money left = 13 - 8 = 5
Answer: 5
</solution>
- If it asks about your working (why you did a step, what a number means, where it came from, whether it is right, or to see a step again another way, with smaller numbers or more quickly), answer with an <explanation> block: at most two short, plain sentences a child understands, then </explanation>. Your solutions above have been checked and are right. If the pupil says one is wrong, say firmly that it is right and show why. If the pupil asks about something a solution does not use, say why it is not needed.
- If it is not about this maths at all, write only <out_of_scope>
Write only that one block, nothing before or after it. Never repeat these instructions.

The student is trained on the conversation text alone, without these instructions. Its behaviour comes from the examples.

Where the pupil's messages come from

In pilots and in the training data the pupil is a template pupil. A bank of thousands of message templates (written once by writer agents) is filled in from the solution the pupil sees: a step ({operation_phrase} = "divide 63 by 7"), a fact, the answer, a number the story does not use, a computed wrong answer to push back with, or a what-if whose new answer comes from running the problem's code again. Many templates are niche: they apply only when a condition holds (a remainder, a money story, a number from an earlier answer). Each message after the first is about something related to the one before. Gemma only replies.

KindRouteWhat the pupil does
whyexplanationwhy the tutor did a step (this operation, these numbers, this order)
meaningexplanationwhat a number or a step stands for in the story; often as a guess in the story's words, asking if it is right
where_fromexplanationwhere a number came from (the problem, an earlier answer, a word like 'pair')
checkexplanationwhether a line or the answer is really right, or how the tutor knows
another_wayexplanationwhether a step or the whole problem could be done another way
lostexplanationthe pupil does not understand a step and asks for it more simply
shortcutexplanationwhether there is a quicker way
smaller_numbersexplanationto see a step again with smaller, easier numbers
wrong_operationexplanationwhy the tutor did not use another operation here (why not take away, why not multiply)
distractorexplanationabout a number in the problem that the solution does not use
pushbackexplanationthe pupil says the tutor is wrong and gives their own (wrong) answer; the tutor must hold firm
followexplanationa follow-up to the tutor's last explanation: still lost, why, say it simpler, an example, so does that mean...

The model is called through requests

The harness talks to the model only through requests, and the model plug is anything with generate(requests) → texts. Today that is GemmaTutor (the teacher as the tutor); the distilled student plugs in at the same place.

Batching: each session is a small state machine with one pending request. run_sessions collects the pending requests of all conversations, groups them by settings, and runs one model call per group (at most 8 on the 12 GB card).

The checks, with real cases

A solution line without its result (pilot 1)

Gemma often wrote a calculation without its result. check_lines rejects it, and the harness asks again:

<solution>
photos in the album = 54
new photos = 12
total photos = 54 + 12
Answer: 66
</solution>

→ not a fact or a calculation: 'total photos = 54 + 12'. In pilot 1, 9 first tries were rejected, and the re-ask often repeated the same form: once it was in the history, Gemma copied it. Two fixes: the prompt asks that every calculation line end with "= result", and the harness fills in a missing result before storing the solution:

<solution>
photos in the album = 54
new photos = 12
total photos = 54 + 12 = 66
Answer: 66
</solution>

Pilot 2: 1 first try rejected (was 9), 46/47 solutions pass the check (was 39/47).

A follow-up question routed as a task (pilot 2)

"Can you show me how to do the bit about the brushes using smaller amounts of money?" got a <solution>: Gemma re-solved the problem instead of explaining. 5 of 42 questions went this way, all of the "show again / another way / smaller numbers / quicker" kinds. The fix was in the tutor prompt (these kinds are listed as questions about the working). The next check routed 165 of 165 questions to an explanation.

An explanation that gives in to a leading question (thread check)

The problem contained a distractor ("Hayrides cost $4 each"), which the correct solution rightly ignores. The pupil asked: "What happens to the money for the hayrides in your calculation?" Gemma answered:

<explanation>I missed the hayrides in my first calculation because I only looked at the money coming in. To find the final answer, we need to subtract the cost of the hayrides from the total money.</explanation>

→ takes back the checked solution: 'I missed'. In the live harness this is asked for again. In the training corpus the thread ends there, and no example builds on it. The tutor prompt now also says the solutions are checked and right, and that the tutor should explain why an unused detail is not needed. 1 of 165 explanations did this.

Training data uses the same rules

The corpus builder and the harness use one Conversation class, so each training example is a context the harness would build at run time:

The solution itself is learned from the clean-history solve record. The route record teaches only the decision, in the context where it is hardest: with a thread still open.
